\chapter*{Foreword}

This document reports the performance benchmark of the one-time-pad keychain. It covers the latency of the keychain operations as seen by the host over USB, the flash and RAM footprint of the keychain firmware, and the CPU and memory usage of the two host applications (SAE node and UserApp).

All keychain latencies come from one complete benchmark run against the real keychain (\texttt{JAVA\_APPS/bench-results/20261022-173859.csv}). The host resource usage comes from a lab run with simulated keychains (\texttt{JAVA\_APPS/bench-results/resources-sim-20261022-170130/}). The firmware footprint comes from the linker scripts and the built ELF images of the firmware project. All times are given in seconds; the raw CSV files store milliseconds.

\section{Lab topology}
\label{sec:topology}

\begin{itemize}
\item \textbf{Keychain benchmark:} one real keychain is connected over USB to the host. The benchmark tool runs on the host inside WSL2 and acts as the UserApp (owner operations, encrypt) and as the SAE (provisioning). The SAE identity is an ephemeral certificate signed by the SAE root CA; no HSM or QKD is involved in the keychain latency figures.
\item \textbf{Host resource measurement:} two simulated keychains (TROPIC01 model with the host build of the firmware, connected through pseudo-terminals), two SAE nodes with the Utimaco HSM simulator (on the Windows side of the same machine, reached over the WSL virtual network) and the remote QuKayDee KME, and two UserApps, one per keychain. All Java applications run on the same host.
\end{itemize}

\chapter{Methodology}

\section{Measured operations}

\benchcard{INIT LAB (enrollment)}{Complete enrollment of a reset keychain for the lab profile, as done by the UserApp without user prompts: owner set, ECC key generation in the TROPIC01, PIN setup, device CSR, signing of the CSR by the client CA on the host and storing the signed certificate on the device.}

\benchcard{OWNER REPLACE (reset)}{Owner reset before every enrollment: wipes the pads, the PIN data, the device key and certificate, the SAE CA and the peers, and keeps the owner. Timed separately from INIT LAB.}

\benchcard{PROVISION (full pad fill)}{The SAE side of a provisioning session: mutual TLS handshake in provisioning mode, verified uplink from the device, ML-KEM sealed downlink of random pads, TROPIC01 wipe and write of all 507 pads into R-MEM, final acknowledgement.}

\benchcard{Handshake (ENCRYPT session)}{Arming of an encrypt session and the PQC mutual TLS~1.3 handshake with the device. The session is closed before any request, so no pad and no PIN try is used.}

\benchcard{Encrypt/decrypt round trip}{One complete UserApp encrypt request: arming, TLS handshake, PIN and plaintext request, reply with one record per pad. The plaintext is 9216\,B (9\,KiB) of printable ASCII, which uses $\lceil 9216/415 \rceil = 23$ pads. Decrypt runs the same path on the device (same session type, framing and per-pad XOR), so this figure stands for both directions.}

\section{Procedure and statistics}

\begin{itemize}
\item The operations run in the order INIT LAB (with OWNER REPLACE) $\rightarrow$ PROVISION $\rightarrow$ handshake $\rightarrow$ encrypt/decrypt, on the same keychain, in one run.
\item Each operation runs 1 warm-up iteration followed by $n = 10$ measured iterations. Warm-up iterations are not counted.
\item The latency is the wall-clock time measured by the host from the first request byte to the final reply, including USB transfer and host processing.
\item Reported statistics: minimum, maximum, mean, median, sample standard deviation and the coefficient of variation (CV = stddev/mean). A 95th percentile is not reported: with $n = 10$ it equals the maximum.
\item Per-iteration timeouts: 120\,s (600\,s for PROVISION). A failed iteration is counted and stops the run for the pad-consuming operations; the reported run has no failed iteration.
\item The encrypt stage reuses one serial link for the warm-up and all iterations, like the UserApp. Its 11 requests use 253 of the 254 encrypt-half pads written by the preceding PROVISION.
\end{itemize}

\section{Host resource measurement}

\begin{itemize}
\item CPU, RSS, peak RSS (VmHWM) and JVM heap of each Java process are sampled every 1\,s. CPU is given in \% of \emph{one} core of the 16-thread host and covers only the Java process (simulators, HSM and KME are excluded).
\item Each JVM additionally records Java Flight Recorder data; the heap used after GC is taken from it.
\item The applications run inside the Maven JVM, so RSS and heap include Maven.
\item Phases are cut from the sample series by timestamps logged by the driver. Phases with operations include short pauses, so the mean CPU is lower than during a single operation; the maximum is the busiest 1\,s sample.
\end{itemize}

\section{Handshake in PROVISION and in ENCRYPT sessions}

The handshake of an ENCRYPT session takes 4.29\,s on average (median 4.14\,s). The handshake of a PROVISION session takes about 10.9\,s on the same keychain. In PROVISION mode the device verifies the SAE certificate chain against the stored SAE CA, which adds post-quantum signature verification on the 48\,MHz Cortex-M33; in ENCRYPT and DECRYPT mode the peer certificate is accepted without that chain verification.

\chapter{Results: host resource usage}

The measurement runs on the host from Table~\ref{tab:hw-host} with simulated keychains (Section~\ref{sec:topology}). The sequence is:

\begin{enumerate}
\item UserApps: idle at the menu, INIT LAB on both fresh simulated keychains, PEER CARD / PEER ADD in both directions;
\item SAE nodes: startup, idle at the operator prompt, PROVISION of keychain 1 by node 1 (new keys generated, QKD key fetch, 237\,KB downlink), then keychain 2 by node 2 (stored keys), both ending with ``Share successful.'';
\item UserApps: encrypt on keychain 1 and decrypt on keychain 2 of 32, 1024, 4096 and 9216\,B messages, three times each, with every decrypted plaintext equal to the original.
\end{enumerate}

The simulated keychain uses 446\,B of plaintext per pad, so a 9216\,B message uses 21 pads there. RSS mostly shows what the JVM reserved and touched (committed heap 248\,MiB, metaspace, code cache, thread stacks and Maven); the memory the application needs is the JFR heap used after GC.

\chapter{Interpretation}

\section{Bottlenecks}

\begin{itemize}
\item \textbf{The keychain is the bottleneck, not the host.} During encrypt/decrypt the UserApp averages 2--8\,\% of one core and during PROVISION the SAE node 6--8\,\%; the host mostly waits for the device.
\item \textbf{PROVISION} is the most expensive operation: 185.18\,s for 507 pads, 0.365\,s per pad including the handshake, the TROPIC01 wipe and the R-MEM writes, an effective rate of 1\,136\,B/s of pad plaintext.
\item \textbf{Encrypt/decrypt} of 9216\,B takes 24.03\,s. The handshake accounts for 4.29\,s (17.8\,\%); the remaining 19.74\,s scale with the 23 pads used, i.e.\ about 0.86\,s per pad. A pad in a request costs more than twice the time of a pad in PROVISION (0.365\,s).
\item \textbf{Owner reset and enrollment} take 57.97\,s together, of which OWNER REPLACE (pad and key wipe) is 35.38\,s and INIT LAB 22.59\,s.
\item \textbf{TLS handshake:} 4.29\,s for an ENCRYPT session and about 10.9\,s for a PROVISION session, which adds certificate chain verification on the device.
\end{itemize}

\section{Scaling}

The encrypt/decrypt latency follows approximately
\[
t(L) \approx t_\text{handshake} + \left\lceil L / 415\,\text{B} \right\rceil \cdot 0.86\,\text{s},
\]
with $t_\text{handshake} = 4.29$\,s, derived from the 9216\,B measurement only. A short message (one pad) is therefore dominated by the handshake (about 5.1\,s estimated); the throughput approaches 415\,B / 0.86\,s $\approx$ 480\,B/s for long messages. PROVISION time scales with the number of pads written; only the full fill of 507 pads is measured.

\section{Stability}

All operations are stable from run to run: the CV is 0.14--0.30\,\% for OWNER REPLACE, INIT LAB and PROVISION and 1.73\,\% for encrypt/decrypt. The handshake varies most (CV 9.71\,\%), caused by one slow iteration (5.46\,s in iteration 2); without it the mean is 4.16\,s and the stddev 0.07\,s.

\section{Resources}

The firmware images leave 26.2\,\% of the flash free (19.9\,\% with the reserved data pages counted as used) and 15.8\,\% of the SRAM unallocated (static data, heap and stack counted). Secure code flash (96.5\,\%) and SRAM4 (99.3\,\%) are nearly full, so further secure features need code-size reduction or a different flash split. At run time the Secure dynamic allocations peak at 68\,KB, well below the 108\,KiB pool. On the host, both applications are idle at about 1\,\% of one core and need a few tens of MiB of live heap.

\chapter{Limitations}

\begin{itemize}
\item One run with $n = 10$ iterations per operation on one keychain; no data across devices, temperatures or USB hosts. The 95\,\% confidence interval half-width of the mean is at most 0.34\,s (PROVISION).
\item Latencies are end-to-end host wall-clock times; the split between USB transfer, MCU computation and TROPIC01 access is not measured.
\item Encrypt/decrypt is measured for one message size (9216\,B); the per-pad cost and the scaling formula are derived, not measured for other sizes. Decrypt is not timed separately.
\item The host is shared with other work (JFR machine CPU load averaged 14--17\,\% over the recordings) and runs inside WSL2, which can affect host latencies and CPU figures.
\item Host resource usage is measured only with simulated keychains; RSS and heap include the Maven JVM.
\item Flash and RAM figures are static sizes from the build; only the peak of the Secure dynamic allocations (68\,KB) is measured, not per operation and not the total RAM usage of the device.
\end{itemize}
