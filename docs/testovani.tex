\chapter*{Foreword}

This report covers automated tests of the Java applications (SAE-node, USER APP, usb-cdc, cert-generator, LabSwitch) and of the SE host / TROPIC01 model.

Java tests live under \texttt{JAVA\_APPS} and are tagged \texttt{unit} or \texttt{integration}. Run them with \texttt{mvn -f JAVA\_APPS/pom.xml test} (with \texttt{env/hsm.env}). The live HSM tests in \texttt{tls-hsm} need the Utimaco simulator; if it is down they fail and Maven skips the downstream modules (\texttt{cert-generator}, \texttt{sae-node}), so add \texttt{-Dmaven.test.failure.ignore=true} to still run every module. Filter with \texttt{-Dgroups=integration} or \texttt{-Dgroups=unit}, or profiles \texttt{-Pintegration} / \texttt{-Punit}. The default run executes both.

Unit tests mock RMI, QKD, and HSM, or use a single SQLite map, a decision table, a parser, framing, store tamper, or status strings. Integration tests drive a real \texttt{NodeCommandsService} on two or three SQLite maps, the production \texttt{ProvisionSession} FSM (including three-node handover via \texttt{ProvisionCluster}), exported RMI, an embedded HTTP KME, a live HSM, a TLS handshake, or multi-node concurrency. Shared-record states are \texttt{RECORD\_SYNCHRONIZATION}, \texttt{RECORD\_FETCHING\_STARTED}, \texttt{RECORD\_SHARED} and \texttt{ORIGIN\_PROVISIONED} (there is no AVAILABILITY enum value).

SE tests are run with \texttt{ctest --output-on-failure -j1} in \texttt{stm32u535-trustzone-usb/host/tropic\_model/build}.

\textbf{Summary (RMI hardening run, 14 Oct 2026):} 357 passed, 2 skipped, 0 failed (347 Java: 345 passed, 2 skipped; 12 SE passed). Java with \texttt{-Punit}: 277 tests, of which 129 in \texttt{sae-node}; with \texttt{-Pintegration}: 70 tests, of which 59 in \texttt{sae-node}. The two skipped tests are \texttt{HsmLiveNoFallbackTest}, which only runs with \texttt{env/hsm.env} sourced and the Utimaco simulator reachable. This run did not source it; the cards below show the earlier run against the simulator, in which they passed. All test classes ran, including ones not described card by card below; Section~\ref{sec:hardening-it} and Section~\ref{sec:hardening-unit} list the tests added for the RMI hardening (F-01, F-02, F-06, F-13).

Since the hardening, every \texttt{NodeCommandsService} call needs an authenticated caller SAE. Over real RMI it comes from the pinned TLS peer certificate. The in-process harnesses (\texttt{ProvisionCluster}, \texttt{TestRmiNetwork}, \texttt{AsCaller}) bind the calling node's SAE ID to each exported stub, so the existing multi-SAE, handover and provision tests above run with the real authorization checks.

\textbf{Previous run (before the RMI hardening):} 338 passed, 0 skipped, 0 failed (326 Java tests in the latest \texttt{mvn -B verify} run with the HSM simulator reachable; 12 SE tests from the previous ctest run). Without \texttt{HSM\_DEVICE} the HSM tests are skipped. New tests and the coverage report are described in the chapter \emph{Test extensions and code coverage}.

\chapter{Test extensions and code coverage}

\section{Test strategy}

Tests in \texttt{JAVA\_APPS} are split with the JUnit~5 \texttt{@Tag} annotation into \emph{unit} tests (\texttt{@Tag("unit")}) and \emph{integration} tests (\texttt{@Tag("integration")}). Unit tests check one class in isolation: collaborators (RMI, QKD client, HSM, USB link) are replaced with Mockito mocks or simple fakes, and they run in milliseconds. Integration tests combine several real components: a real TLS handshake, exported RMI over TLS, an HTTP KME server, SQLite databases or the HSM simulator. Tests that need the HSM also carry \texttt{@Tag("hsm")}.

The parent \texttt{pom.xml} passes the \texttt{groups} property to Surefire. Its default is empty, so \texttt{mvn -B verify} runs both groups. Profiles limit the run to one group:
\begin{itemize}
  \item \texttt{mvn -B verify -Punit} -- unit tests only,
  \item \texttt{mvn -B verify -Pintegration} -- integration tests only (including the HSM tests when the simulator is reachable).
\end{itemize}

The new integration tests live in the \texttt{fel.cvut.integration.*} packages. The TLS and HSM tests share the \texttt{src/SaeNode/test} source tree but are assigned to the \texttt{tls-software} and \texttt{tls-hsm} modules via \texttt{testIncludes} and removed from \texttt{sae-node} via \texttt{testExcludes}. Production code (\texttt{src/*/main}) was not changed while extending the tests; the later RMI hardening (Section~\ref{sec:hardening-it}) did change it.

\section{New integration tests}

\subsection{TLS between two nodes (tls-software)}
\subsubsection{integration / tls}

The tests generate an ML-DSA root CA and \texttt{sae-1} / \texttt{sae-2} leaf certificates (PEM and PKCS12) in a temporary directory and open real TLS connections through \texttt{SoftwareTls}.

\testcase{SoftwareTlsTwoNodeTest.mutualPqcHandshakeAndApplicationDataBothDirections}{passed}{A PEM context and a PKCS12 context complete a mutually authenticated pure post-quantum handshake, data flows in both directions and each side sees the peer's CN.}

\testcase{SoftwareTlsTwoNodeTest.classicalProfileClientNegotiatesPqcWithPureServer}{passed}{A client with the \texttt{CLASSICAL} profile negotiates with a server in the \texttt{PURE\_PQC} profile.}

\testcase{SoftwareTlsTwoNodeTest.nodeFromForeignCaIsRejectedByServer}{passed}{The server rejects a client whose certificate comes from a foreign CA.}

\testcase{SoftwareTlsTwoNodeTest.clientRejectsServerFromForeignCa}{passed}{The client rejects a server whose certificate comes from a foreign CA.}

\testcase{SoftwareTlsTwoNodeTest.deviceLeafIssuedFromRawKeyAuthenticatesOverWrappedTransport}{passed}{A leaf issued from a raw ML-DSA-44 key (\texttt{SoftwareLeaf}) authenticates through \texttt{SoftwareTls.wrapServer} over an already open transport.}

\testcase{SoftwareTlsTwoNodeTest.trustStoreHelpersRoundTrip}{passed}{The \texttt{TlsStores} helpers (trust store from a certificate, PKCS12 loading, leaf from PKCS12) return the original certificates.}

\subsection{RMI between two nodes (sae-node)}
\subsubsection{integration / rmi}

Two \texttt{RmiManager} instances run in one JVM over TLS (\texttt{PURE\_PQC}). The registry uses port $p$ and the export uses port $40000+p$, so the test picks a free port pair at runtime. \texttt{connectBySaeId} reads fixed ports from \texttt{sae-nodes.json}, so the origin side uses a Mockito \texttt{spy} redirected to \texttt{connect(Address)}. No environment variables are needed.

\testcase{RmiTlsTwoNodeTest.pingAndRecordQueriesTravelOverRmiTls}{passed}{\texttt{ping}, \texttt{synchronize}, \texttt{lockFetch}, \texttt{getRecordMetadata} and \texttt{removeRecord} go over real RMI and change the peer database.}

\testcase{RmiTlsTwoNodeTest.fullExchangeOverRealRmiFinalizesBothDatabases}{passed}{A full \texttt{PeerRecordSync} exchange with a mock KME: both rows end RECORD\_SHARED, the peer key material matches the origin, and \texttt{markOriginProvisioned} over RMI leads to ORIGIN\_PROVISIONED.}

\testcase{RmiTlsTwoNodeTest.peerRefusalPropagatesAsRemoteExceptionOverTheWire}{passed}{An \texttt{insert} without a reservation is refused by the peer, the client gets a \texttt{RemoteException} and the database stays empty.}

\testcase{RmiTlsTwoNodeTest.stopUnexportsAndSameAddressCanBeRestarted}{passed}{A repeated \texttt{start} has no effect, after \texttt{stop} the old stub fails, and the node can be started again on the same address.}

\subsection{ETSI QKD 014 flow into SQLite (sae-node)}
\subsubsection{integration / qkd}

A mock KME (\texttt{MockKme}, \texttt{com.sun.net.httpserver}) implements \texttt{status}, \texttt{enc\_keys} and \texttt{dec\_keys} (GET and POST). Origin and peer both use a real \texttt{Qkd014Client}; the peer is a real \texttt{NodeCommandsService} on its own SQLite database.

\testcase{Qkd014KeyExchangeFlowTest.keysFlowFromKmeIntoBothDatabases}{passed}{Keys from \texttt{enc\_keys} reach the peer through \texttt{dec\_keys}, both rows are RECORD\_SHARED, the peer's stored (sealed) material equals the origin's, and every issued ID is consumed.}

\testcase{Qkd014KeyExchangeFlowTest.largeKeyIdListIsBatchedThroughPost}{passed}{With small keys and \texttt{max\_key\_per\_request}=2 the ID list is split into several \texttt{dec\_keys} batches; the result is identical on both sides.}

\testcase{Qkd014KeyExchangeFlowTest.peerKmeRefusalRollsBackBothSides}{passed}{The peer's KME answers HTTP 400: the exchange ends with \texttt{RemoteException} and both reservations are rolled back with no key material.}

\subsection{HSM simulator (tls-hsm)}
\subsubsection{integration / hsm}

\texttt{HsmSimulatorTest} tests \texttt{Pqmi}, \texttt{HsmAesGcm} and \texttt{HsmNodeTls} against a running Utimaco CryptoServer simulator. It runs only when \texttt{HSM\_DEVICE} is set and the given \texttt{port@host} accepts TCP connections; otherwise the whole class is skipped via \texttt{Assumptions} (reported by Surefire as 0 tests run). It only creates keys with the \texttt{it-sim-} prefix, so existing simulator state is left alone. Run it with:
\begin{center}
\small\texttt{HSM\_DEVICE=3001@<host> HSM\_TIMEOUT\_MS=60000 HSM\_USER=CXI\_HMAC HSM\_PIN=\ldots{}} \\
\small\texttt{HSM\_MLDSA\_GROUP=JAVA\_APPS HSM\_MLDSA\_SPEC=0 mvn -B verify}
\end{center}
From WSL, a simulator running on Windows is reachable via the host IP (e.g.\ \texttt{172.28.0.1}), not via \texttt{127.0.0.1}. The Linux simulator in the GP~6.5 package is 32-bit and needs i386 libraries; the tests used the simulator already running on port 3001.

\testcase{HsmSimulatorTest.aesGcmRoundTripUsesHsmKey}{passed}{The AES-GCM key is created in the HSM idempotently, every encryption uses a fresh IV, and decryption returns the original data.}

\testcase{HsmSimulatorTest.aesGcmDetectsTamperingAndUnknownAlias}{passed}{A modified ciphertext and a non-existent key alias both throw instead of returning wrong output.}

\testcase{HsmSimulatorTest.pqmiIdentityKeySignsVerifiablyWithMlDsa44}{passed}{PQMI generates an identity key, refuses to overwrite it, exports a 1312\,B public key, and BouncyCastle ML-DSA-44 verifies the HSM signature.}

\testcase{HsmSimulatorTest.hsmBackedNodeCompletesPqcHandshakeWithSoftwarePeer}{passed}{\texttt{HsmNodeTls.createContextForNode} with the key in the HSM completes a mutual PQC handshake with a software node.}
