\noindent
The \texttt{PROVISION} command fills the chip with one-time pads from QKD.
The SE opens TLS only if \texttt{se\_\allowbreak ready\_\allowbreak provision()}
holds (owner, device certificate and key, SAE CA, ML-KEM key) and its clock is
synchronised. After the mTLS handshake it sends a version~5 uplink bound to the
TLS exporter (\texttt{SeSessionUplink.\allowbreak readAndVerify}) and, in
parallel, erases its QKD R-MEM slots; it signals completion with
\texttt{TROPIC\_\allowbreak WIPE\_\allowbreak FINISHED}.
Figure~\ref{fig:provision-flow} shows the SaeNode decision tree: the operator
selects the peer SAE and the peer device, and the node looks up its own
\texttt{client\_\allowbreak record\_\allowbreak state} row for the pair. Without
a row the operator may generate new keys; a row of a share with the selected
SAE that another SAE issued is a stored share for this device; for any other
row the operator keeps the keys or deletes them.

Every operation on a client pair (new share, delivery of a stored share,
operator delete) runs under a \emph{pair lock} on both SAEs of the pair
(\texttt{PairLocks}, \texttt{PairLockRegistry}). The lock is keyed by the
sorted pair of client hashes and kept in memory. The operation takes the lock
of the SAE with the lower ID first and then the lock of the SAE with the
higher ID, over RMI \texttt{lockPair} for a remote SAE. If a lock is refused,
the first one is released and the operator sees \texttt{Another operation for
this device pair is in progress on an SAE. Retry later.}; nobody waits for a
lock. A lock is a lease of 5~minutes with a random 128-bit token and the
issuing SAE. The holder renews both leases every 60\,s (\texttt{renewPair})
and synchronously before and after each commit step
(\texttt{PairOperation.\allowbreak checkpoint}); a failed renewal aborts the
operation and closes the device session. Every row write and delete runs in
one \texttt{BEGIN IMMEDIATE} transaction that checks the token, expiry and
issuer of the lease. At the end the operation releases both locks by token,
the remote one first (\texttt{releasePair}).

For a new share the origin SAE, holding both locks, checks that no local row
has appeared and reads the target row over RMI; a target row that names a
third SAE leads to the delete prompt. The origin then fetches key IDs and pads
from its KME, renews both locks and sends the downlink to the device, renewing
both locks every 60\,s during the transfer. After the chip answers
\texttt{SE\_\allowbreak OK}, the origin renews both locks, the peer writes
\texttt{KEYS\_\allowbreak AVAILABLE} with the operation token (RMI
\texttt{insert}: the peer resolves the same pads by key ID at its own KME and
stores them wrapped by the HSM, in one transaction under the caller's lease),
and then the origin writes its own \texttt{KEYS\_\allowbreak AVAILABLE} row
with the token. After a final renewal of both locks the terminal prints
100\,\% followed by \texttt{Share successful.} on the next line. If a write
fails, the peer row is deleted by token and the node logs a warning that the
device stored the keys but the share could not be recorded on both SAEs.

The peer chip receives its material later. Under both locks the peer SAE
checks that its row still carries the token shown to the operator and reads
the origin row over RMI; the share is delivered only when both rows are
\texttt{KEYS\_\allowbreak AVAILABLE}, carry the same token and issuer and name
each other. The peer SAE then deletes the row on the origin, then its own row,
both by token, and only then sends the downlink. A share that fails this check
is deleted as an orphan, remote first, without delivery.

An operator delete locks both SAEs of the shown share, re-reads the shown row
and deletes the counterpart row first and the shown row last, each only if it
still carries the token the operator saw (compare-and-delete, RMI
\texttt{deleteRecord}). Otherwise nothing is deleted and the operator is asked
again. Every RMI call runs over mTLS with a pinned peer SPKI, and the caller's
SAE ID comes from its certificate; lease calls, \texttt{insert} and
\texttt{deleteRecord} act only on a lease the caller holds.

Two limitations are open. A device may hold keys after a failed commit without
\texttt{Share successful.}; the operator provisions both devices again. The
locks are kept in memory, so an SAE restart releases all of its locks, and
operations that held one fail at their next renewal or fenced write.

\section{Formal verification}
\label{sec:provision-formal}

The TLA+ model \texttt{specs/sae-provision/SaeProvision.tla} (plain TLA+, no
PlusCal) verifies this protocol for several SAEs, several concurrent
provision attempts, operator deletes and faults. Each attempt is given as a
triple $\langle$origin, peer, device$\rangle$ in the constant \texttt{Edges};
all attempts concern one client pair, so every SAE has one lock entry and one
row per device for that pair. A lock entry is
$[\mathit{iss}, \mathit{tok}, \mathit{st}]$ with the state \texttt{free},
\texttt{held} (the holder renews it) or \texttt{lapsing} (nobody renews it and
\texttt{Expire} may free it at any time); time is abstract. A row is
\texttt{none} or \texttt{KEYS\_AVAILABLE} with issuer, counterpart SAE, token
and key material. An attempt runs the steps \texttt{lock1} (lower SAE ID),
\texttt{lock2} (higher SAE ID), \texttt{check} (keep or delete an existing
share), \texttt{kme}, \texttt{xfer}, \texttt{pwrite} (peer write fenced by
its lock entry), \texttt{owrite}, \texttt{complete} and the releases
\texttt{relR}, \texttt{relL}, remote first. An operator delete takes both locks
with a new token, deletes the remote row and then the local row by
compare-and-delete, releases and provisions again.

The faults are: \texttt{LostReply} (the reply of a remote acquire, insert,
delete or release is lost; the handler runs later, fenced by its token),
\texttt{Stall} (the holder stops renewing, its entries lapse and may expire),
\texttt{AbortOp} (KME or renewal failure), \texttt{RenewFails} (a renewal finds
an entry without the token), and \texttt{Crash} (all lock entries of the SAE
are lost, rows survive, its session ends without \texttt{Share successful.}).
After a renewal gap the holder renews both entries before its next step
(\texttt{LeaseGuard}). TLS, the PIN, pad bytes, record retention and more than
one client pair are not modelled.

The constants \texttt{MaxSessions}, \texttt{MaxCrashes}, \texttt{MaxStalls},
\texttt{MaxAborts} and \texttt{MaxLost} bound the state space;
\texttt{OperatorDeletes} allows operator deletes and \texttt{RetryOnRefusal}
lets a refused attempt retry in the same session. The constants
\texttt{LockOrder}, \texttt{FencePeerWrite}, \texttt{DeleteTakesLocks},
\texttt{DeleteChecksSeen} and \texttt{LeaseGuard} select the guards; every
configuration in Table~\ref{tab:provision-tlc} uses the design values
(\texttt{"lower"} and \texttt{TRUE}). Every configuration checks for deadlock
(\texttt{CHECK\_DEADLOCK TRUE}). \texttt{SaeProvision}, \texttt{\_fan},
\texttt{\_chain} and \texttt{\_ring} also check the liveness property
\texttt{AllSagasFinish}: eventually every attempt terminates.
\texttt{\_races} and \texttt{\_racesfull} combine concurrent sessions,
operator deletes, stalls and lost replies (\texttt{\_racesfull} adds a crash)
and check safety only.

\noindent
In all reachable states of the six configurations the following invariants
hold:

\begin{itemize}
  \setlength{\itemsep}{0.15em}
  \item \texttt{TypeOK}: every variable stays in its domain.
  \item \texttt{MutualExclusion}: two operations that hold both of their lock
        entries never share an SAE.
  \item \texttt{TerminalSuccessMeansConsistentShare}: \texttt{Share
        successful.} is reported only when both rows are
        \texttt{KEYS\_AVAILABLE} with the attempt's token and key material and
        the origin device holds those pads.
  \item \texttt{OriginMarkedAfterPeer}: the origin writes
        \texttt{KEYS\_AVAILABLE} with a token only while the peer row already
        carries it.
  \item \texttt{MatchingSharesWhenCommitted}: two counterpart rows with the
        same token hold the same key material.
  \item \texttt{NoMismatchedDelivery}: a peer device receives only the pads of
        the attempt whose rows it checked, and the origin device of that
        attempt holds them.
  \item \texttt{CompletedShareNotSilentlyLost}: a share reported as complete
        stays intact until an operator delete removes it.
  \item \texttt{OperatorDeleteOnlyConfirmedShare}: an operator delete removes
        only the share the operator confirmed.
  \item \texttt{OperatorDeleteOnlyRowsPresentAtLock}: an operator delete
        removes only rows present when it held both locks.
  \item \texttt{RemoteFirstDelete}: a local delete runs only after the remote
        delete succeeded.
\end{itemize}

\noindent
The ring configuration is the candidate for a distributed deadlock: every SAE
is the origin of one attempt and the peer of another, and refused attempts
retry. TLC finds no deadlock and no liveness violation, because every
attempt takes the lower SAE ID first.

\noindent
The implementation and the model share the following guards.

\begin{itemize}
  \setlength{\itemsep}{0.15em}
  \item One session per SAE: \texttt{Node.usbLoop} serves one device at a
        time (\texttt{usb[n]}).
  \item Lock order: the lock of the lower SAE ID is taken first; a refusal
        releases the first lock by token and ends the attempt
        (\texttt{LockOrder}).
  \item Fenced peer write: the peer writes \texttt{KEYS\_AVAILABLE} only under
        a live lease of the caller with the operation token, in one
        transaction with the key material (\texttt{FencePeerWrite}).
  \item Origin write after the peer write, both after the device ack.
  \item Renewal of both locks after a gap: \texttt{PairOperation.checkpoint}
        runs before and after each commit step (\texttt{LeaseGuard}).
  \item Operator delete under both locks (\texttt{DeleteTakesLocks}), remote
        first, by compare-and-delete on the token the operator confirmed
        (\texttt{DeleteChecksSeen}).
  \item Use-time token match: a stored share is delivered only when both rows
        carry the same token, and both rows are deleted, remote first, before
        the downlink.
  \item Device reads time out after 100\,s during the handshake and uplink and
        after 15 minutes during the wipe, key transfer and ack; a timeout ends
        the session.
\end{itemize}

\noindent
Each guard switched off on its own makes TLC fail
(Table~\ref{tab:provision-mutations}); the mutation configurations are in
\texttt{specs/sae-provision/mutations/}.
